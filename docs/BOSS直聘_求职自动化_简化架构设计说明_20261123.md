# BOSS直聘求职自动化 简化架构设计说明

> 文件用途：把旧项目的失败证据、本次真机验证结论和“最简可行架构”合并成一份设计说明，供后续实现业务 CLI、运行时状态与设备执行器时对照。本文只描述结构与判据，不包含真实聊天内容、联系人、公司、薪资或联系方式，也不构成任何设备执行授权。

## 0 范围与依据

- 目标系统：单台 Android 手机、单条 ADB、串行执行；不做并行、不做无人值守的不可逆批量发送。
- 业务目标（使用者定义）：
  1. 浏览新职位，创造沟通机会。
  2. 读取并回复 HR 消息，判断意图。
  3. 归档已拒绝或过期的会话。
- 证据来源：
  - 旧项目代码静态阅读（`scripts/` 下 `core/`、`hr/`、`jobs/`、`heartbeat/`）。
  - 旧项目 `data/operations.log` 的事件名与原因码**计数**（仅聚合，未读取任何业务内容）。
  - 一次真机验证（BOSS 14.200、Android 15、1080×2400），记录见 [`BOSS直聘_实机验证偏差与修订建议_20261123.md`](BOSS直聘_实机验证偏差与修订建议_20261123.md)。
  - 旧项目操作手册：[`BOSS直聘_手机客户端原始操作_原子化分析.md`](BOSS直聘_手机客户端原始操作_原子化分析.md)。
- 本文是设计说明，不是实施计划；里程碑与排期另行编写。

## 1 背景：旧项目输在哪

### 1.1 失败分布

旧项目 `apply` 事务 352 次的失败构成（来自操作手册 §1.2）：LLM 判断错误（`evidence_not_in_message` + `policy_violation`）约 13 次，占 3.7%；其余绝大多数是页面、读屏与动作结果未知。

这说明：**问题不在“模型不会判断”，在“感知不可靠 + 状态不属于程序”**。

### 1.2 三个根因

| 根因 | 代码证据 | 后果 |
|---|---|---|
| 循环变量住在 LLM 上下文 | 操作手册 §1.3 的复盘结论 | 失败无法局部化；上下文随轮次累积（单次 `hr scan` 输出 37 KB） |
| 自动回复被策略层关死 | `policy.py:132-133` 禁止 `needs_human`/`uncertain` 发送；`status.py:12-13` 把约面试、薪资、背调、敏感信息都归入 `needs_human` | 大量真实 HR 场景只能出草稿，表现为“经常转人工” |
| 未读判定 fail-open | `message_list.py:264-269` 只认 `:id/badge_view`；`scan.py` 的 `_message_tab_badge` 读底部 tab 数字；`scan.py:1964-1979` 在角标读不到时按 0 处理并继续 | 读不到被当成“没有未读”，静默漏读 |

补充约束：

- `policy.py:14`、`apply.py:548`：首条回复必须含固定声明，否则 `policy_violation`。
- `policy.py:114-118`：决策 `evidence` 必须是原文子串。
- `policy.py:70-74`、`141-143`：规则引擎默认 `uncertain`，并可一票否决 LLM。
- `scan.py:1989-1990`：任一未核实动作会让整轮未读扫描停摆。

### 1.3 日志计数（累计，非每轮比率）

`operations.log` 共 364,538 行、71 类事件。关键计数：

| 类别 | 计数 | 说明 |
|---|---:|---|
| `adb_start` / `adb_finished` / `adb_failed` | 107,150 / 107,093 / 41 | 传输层失败率约 0.04% |
| `no_direction_evidence` | 1,916 | 无法证明消息方向 |
| `followup_read_incomplete` | 1,137 | 旧 followup 读不全（功能已退役） |
| `latest_message_not_incoming` | 931 | 期望最新入站，实际不是 |
| `executor_error` | 345 | 执行器异常 |
| `filter_unverified` | 311 | 未读筛选无法确认 |
| `read_incomplete` | 289 | 读取不完整 |
| `needs_probe` | 239 | 动作结果待探测 |
| `menu_unverified` / `delete_unverified` | 142 / 148 | 清理链路核验失败 |
| `badge_unknown_rows` | 13 | 角标未知，静默漏读源 |
| `post_reply_followup_unknown` | 2,783 | 发送后状态无法确认，最大单类不确定 |
| `unread_filter_applied` / `retap` / `failed` / `entry_absent` | 170 / 41 / 29 / 22 | 筛选交互约三分之一需要重按或失败 |

结论：**重试不是主要矛盾；“判不出来时怎么办”才是。** 传输层稳定，语义与结构判读不稳定。

## 2 设计原则

1. **程序持有循环与状态**：队列、租约、重试预算、断点恢复都在 SQLite，不在模型上下文。
2. **模型只回答单条决策**：无状态、窄输入、受 schema 校验；不排序、不计数、不审核。
3. **照实分三态**：`ok / failed / undetermined` 必须分开，`undetermined` 不得当成“空”或“否”。
4. **只有不可逆动作需要原子化**：发文本、发简历、换微信、换电话、删会话；其余用少量设备原语组合。
5. **证据优先于文案**：系统行、槽位状态、节点增量是证据；弹框文案、Toast、截图不是。
6. **默认不重试**：只有可证明的瞬态错误才重试，其余停下并记原因码。

## 3 总体架构

```
┌──────────────────────────────────────────────┐
│ 传感器（程序）                                │
│  未读四源：行内数字 / 新招呼计数 / 底部角标 / 预览基线 │
│  职位候选、清理候选                            │
└───────────────┬──────────────────────────────┘
                │ 结构化候选（≤2 KB）
┌───────────────▼──────────────────────────────┐
│ 循环与队列（程序）                            │
│  任务级优先级：未读 > 新消息读取 > 职位 > 归档   │
│  安全点抢占 + 有界延迟 + 批次游标              │
│  租约、幂等键、重试预算、断点恢复              │
└───────────────┬──────────────────────────────┘
                │ DecisionEnvelope
┌───────────────▼──────────────────────────────┐
│ 单次决策（模型，无状态）                      │
│  意图 / 措辞 / 单条职位评估 / 异常裁决         │
└───────────────┬──────────────────────────────┘
                │ Decision（受校验）
┌───────────────▼──────────────────────────────┐
│ 执行与验收（程序）                            │
│  设备原语 + 5 个不可逆动作护栏 + 三态证据      │
└───────────────┬──────────────────────────────┘
                │ 仅 unknown
                ▼
         人工核对卡 / 下一轮
```

没有主 LLM，没有独立队列服务，没有逐条截图审核，没有多 agent 并行。

## 4 数据流与调度

### 4.1 一轮数据流

1. 传感器从业务表计算候选，合并多源未读证据；任一源为“有”即认为有未读，全部为“不可读”时暂停并报告。读取按 §5.4 的四级阶梯逐级下降。
2. 循环按固定优先级取一条候选，写入租约（`lease_owner`、`lease_expires_at`）。
3. 程序拼装 `DecisionEnvelope`，调用一次模型；输出经 schema 与证据校验。
4. 程序按策略分档决定发送、草稿或转人工；不可逆动作走护栏。
5. 证据写回业务行，释放租约；`unknown` 标 `blocked` 并生成核对卡。

### 4.2 任务粒度与抢占

需求是“未读一直优先”。因此不能把职位批次当成一个不可分割的任务，否则批次运行期间到达的未读只能等待。

#### 4.2.1 任务粒度

| 对象 | 建模方式 |
|---|---|
| 一条未读消息 | 一个任务 |
| 一条职位 | 一个任务（打开 → 采集 → 沟通 → 资源消息 → 回列表） |
| 一个职位批次 | 游标 + 预算，**不是任务**；可随时暂停与恢复 |
| 一条清理候选 | 一个任务 |

批次不再是调度单元。20 条职位是 20 个任务加一个游标。

#### 4.2.2 每次取任务重算优先级

```python
# 调度设计伪代码：状态未知先核对，每次只执行一个任务。
while budget_ok():
    refresh_candidates()  # 优先复用安全点取得的当前快照
    if unread_unknown():
        verify_unread_once()
        if unread_unknown():
            pause("unread_unverified")
            break
    if unread_pending():
        if switching_from_job() and preemption_limit_reached():
            pause("preemption_limit")
            break
        task = next_unread()
    elif new_messages_pending():
        task = next_new_message()
    elif jobs_pending():
        task = next_job()
    elif cleanup_allowed():
        task = next_cleanup()
    else:
        break
    run(task)  # 不可逆动作仍须满足本轮授权与护栏
    checkpoint()  # 只有 §4.2.3 的全部条件满足后才能再次取任务
```

优先级不是“整段顺序”，而是每个任务取用前重新判定。“新消息读取”指已有会话基线发生变化、但没有明确未读角标的候选，不是再次处理同一条未读消息；两类候选按会话身份与入站消息身份去重。伪代码只表达调度分支，不代表当前仓库已有这些函数。

持续存在可处理未读时，严格优先级仍可能让职位等待；本文不承诺职位无饥饿。达到轮次预算或抢占上限时保存游标并暂停，不通过降低未读优先级保证职位进度。

#### 4.2.3 只允许在安全点抢占

| 可抢占 | 不可抢占 |
|---|---|
| 一条职位处理完并已回到列表 | 点击发送/沟通的瞬间 |
| 输入框为空、无确认框 | 正在输入文本 |
| 无在途 ADB 命令 | 确认框已打开未确认 |
| 上一动作状态已写库 | 动作 `pending` 未收敛 |

左列条件必须同时满足，不是任选其一。`pending` 或 `unknown` 尚未核实时暂停并生成核对卡，不继续取任务。中途打断会留下“点了一半”的现场，正是 `unknown` 的主要来源之一。

#### 4.2.4 抢占检查优先复用已有读取

职位任务结束回到列表时，优先复用该次读取中实际可见的消息角标；只有当前页面包含相应节点时，才能解析“新招呼”计数。快照缺少信号或已失效时走 §4.2.5，不能把信号缺席当成零，也不保证检查始终不增加设备调用。旧项目已有类似复用优化：提交 `8a25ac9 perf(hr): 复用发送后层级与返回列表快照减少重复读屏`。

#### 4.2.5 角标不可读时 fail-closed

1. 首次读不出：在安全点允许一次定向核对，切到消息页读取；有未读则留在消息页处理，确认无未读才返回职位列表。耗时纳入本轮预算，具体耗时待实测。
2. 仍读不出：暂停批次，记 `unread_unverified`，本轮不再执行不可逆职位动作。
3. 不做清理：清理依赖“无未读”前提，未读状态不明时一律不删。

#### 4.2.6 有界延迟

| 指标 | 目标 |
|---|---|
| 未读检查间隔 | 正常职位流程每完成 1 条就检查；事务建议 ≤ 30 秒 |
| 首次观察到未读 → 开始处理的调度等待 | 下一个安全点优先取未读；记录实测耗时 |
| 单条职位事务耗时上限 | 建议 ≤ 30 秒；超时停止发起后续动作，先核实在途结果并保存状态，再暂停，不强制中断 |
| 单轮抢占次数 | 建议 ≤ 5 次；再次需要抢占时保存游标并暂停本轮，不能继续职位或清理 |

“未读优先”的正常路径目标是**最多等待一条职位事务，再加检测与切页耗时**。轮询无法获知消息实际到达时刻，不能把首次观察时间当作到达时间；“到达后 ≤ 30 秒”目前不是可证明的硬保证。超时、状态未知或设备中断走暂停与核对，单独记录，不能算作按时开始处理。

#### 4.2.7 批次游标按身份恢复

列表会滚动、会插入新职位，下标不可靠。游标保存：

```json
{"batch_id": "...", "last_job_dedupe_key": "...",
 "visited_keys": ["..."], "remaining_budget": {"count": 12, "seconds": 420}}
```

恢复时按 `dedupe_key` 重新定位；找不到就跳过，不按“第 7 条”硬点。

#### 4.2.8 抢占记录

```json
{"event": "stage_preempted", "from": "job", "to": "unread",
 "job_key": "...", "trigger": "unread_count>0",
 "first_observed_at": "<timestamp>", "handling_started_at": "<timestamp>",
 "waited_ms": 12000}
```

`waited_ms` 是首次观察到未读至开始处理的耗时，运行内用单调时钟计算；时间字段用于本机审计。检测间隔另记连续检查的时间差。该事件在实际切换并开始处理时写入；超时、达到抢占上限或未能进入安全点则写暂停原因，不能伪造已开始处理的事件。没有这些记录，“优先”就无法被审计。

#### 4.2.9 不做

- 不在点击、输入、确认框期间抢占。
- 不杀进程来“抢占”。
- 不让模型决定抢占时机。
- 不让清理抢占任何阶段。
- 不把“整个未读阶段跑完”或旧快照中的“未读为空”作为启动职位批次的门槛；每条任务仍按当前候选优先级选择，未读状态未知先核对。

## 5 接口

### 5.1 DecisionEnvelope（输入）

```json
{
  "kind": "hr_message | job_card | anomaly",
  "subject": {"conversation_key": "<hash>", "job_brief": "<一句话摘要>"},
  "inbound": "<本次要处理的原文>",
  "context": ["<可选的上一两条入站>"],
  "allowed_facts": [
    {"key": "work_location", "value": "<值>", "source": "user_confirmed", "expires_at": null}
  ],
  "policy_tier": "A | B | C",
  "constraints": {"max_chars": 300, "no_contact": true, "max_bytes": 2048}
}
```

约束：一次只含一个主体；所有事实带来源与有效期；不包含队列、日志、其他会话或截图。

### 5.2 Decision（输出）

```json
{
  "intent": "rejected | declined | interested | needs_human | uncertain",
  "sub_intents": ["<受词表约束>"],
  "reply": "<text>",
  "evidence": "<必须是 inbound 的子串>",
  "escalate": null
}
```

校验失败即丢弃，不回写；`evidence` 非子串按 `stale_evidence` 处理。

### 5.3 ReadResult（三态）

```
ok           : 读到且结构完整（唯一列表、唯一输入框、身份一致）
failed       : 明确失败（页面不对、元素不存在、断连）
undetermined : 读到了，但无法判定（角标未知、方向不明、身份不唯一）
```

`undetermined` 不得参与“没有未读”“已经发送”“已经删除”的结论。

### 5.4 读取阶梯与视觉兜底

主路径永远是程序的结构化读取；视觉只在主路径判不出来时补位，且只输出字段、不产出操作。

#### 5.4.1 四级阶梯

| 级别 | 手段 | 触发 | 输出 | 可校验性 |
|---|---|---|---|---|
| 1 | 层级 XML（`uiautomator dump`） | 默认 | 页面、行、方向、身份、正文、按钮 | 高：节点与文本可复核 |
| 2 | 像素/几何（原始 `screencap`） | 层级不含该状态（如红点角标） | 有无未读、角标计数、控件是否禁用 | 中：依赖阈值与分辨率 |
| 3 | 视觉模型判读（截图） | 1、2 对该字段均为 `undetermined` | 页面类别、未读条数、控件状态 | 低：需交叉校验 |
| 4 | 人工核对 | 3 仍不确定，或涉及不可逆动作 | 结构化结论 + 现场截图 | 最高 |

每级结果都带 `source` 与 `confidence`。低级别不得覆盖高级别已确认的结论，只能补充未决字段。

#### 5.4.2 为什么第 2 级不是可选项

旧项目标定文档 `docs/未读状态图像识别标定记录_20261116.md` 记录：该设备/版本上 BOSS 没有把未读状态暴露给无障碍层级，唯一信号是头像右上角红点，只能像素采样；判据为 `badge_view` 区域强红像素 ≥ 100，核心色与容差需按机型重标定。

同一天的提交也说明单源不稳：

- `1f33da9` 未读识别改用 `badge_view` 红像素阈值判定
- `e6c28d1` 移除顶部分类计数兜底，未读只信像素判据
- `fe93ea3` 未读角标不可判定时用消息数字角标兜底，不静默当作无未读（提交说明记录了 2026-11-20 实测的 `no_more_unread` 假阳性与漏读）
- `a2a322d` 用视口像素覆盖 B 段与末页审计

2026-11-23 真机验证又出现第三种形态：未读是无 `resource-id` 的数字 TextView，并伴随“新招呼”的 `tv_count`。同一结论：信号形态随版本漂移，不能写死单源。

#### 5.4.3 视觉兜底的触发与输出

触发必须同时满足：

- 第 1、2 级对该字段均为 `undetermined`
- 该字段影响下一步决策（例如“有没有未读”“当前是不是聊天列表”）
- 不处于不可逆动作的发送后核验阶段

输入：一张当前屏幕截图 + 需要判定的字段清单。输出只允许结构化字段：

```json
{
  "page": "chat_list | chat_detail | job_detail | unknown",
  "unread_rows": 0,
  "badge_count": null,
  "confidence": "low | medium | high",
  "source": "vision",
  "notes": "<不超过 80 字，不得复述聊天正文>"
}
```

校验：字段必须在白名单内；`confidence=low` 或字段缺失时按 `undetermined` 处理；`notes` 不得包含原文片段。

#### 5.4.4 禁止用途

- 不作为“已发送/已删除”的证据：这类结论需要点击前后的时序对比，单张截图无法证明。
- 不直接产出点击坐标或操作指令。
- 不替代第 1 级的批量读取（成本高、不可复现）。
- 不在 `confidence=low` 时继续不可逆动作。

#### 5.4.5 隐私与授权

截图含真实聊天画面。调用云端视觉模型属于把真实业务数据外发，必须满足其一：本机模型；使用者逐次明确授权；截图先脱敏（打码姓名、公司、正文）。默认走第 4 级人工核对。

### 5.5 不可逆动作契约

| 动作 | 前置 | 幂等键 | 证据 |
|---|---|---|---|
| 发文本 | 正文回读一致、授权有效 | `conversation:reply` | 系统行/回显新增 |
| 发简历 | 确认框附件名匹配 | `conversation:resume` | “附件简历请求已发送”记 `request_sent`；“附件简历已发送”记 `sent` |
| 换微信 | 槽位可点击、未处理 | `conversation:wechat` | 槽位“请求中”/系统行 |
| 换电话 | 同上 | `conversation:phone` | 同上 |
| 删会话 | 身份唯一、保护项为空、已确认 | `conversation:delete` | 目标不再出现且锚点仍在 |

统一流程：写 `pending` → 执行 → 判三态 → `unknown` 标 `blocked`，**绝不重试**。

### 5.6 策略分档

| 档 | 意图 | 处理 |
|---|---|---|
| A | 正向招呼、明确要简历、简单岗位问答 | 直接发送 |
| B | 约面试、谈薪资、要 JD、需要附件 | 生成草稿，人工一键 |
| C | 可疑、敏感信息、纯图片/语音、语义歧义 | 只登记待办 |

分档是配置，不是代码分支；模型无权改变档位。

## 6 数据模型

复用业务表，不新建队列：

```sql
-- 示例：HR 消息即可作为队列
-- priority 只用于同类型内排序；跨类型（未读/职位/清理）顺序由 §4.2 调度器决定
ALTER TABLE hr_messages ADD COLUMN lease_owner TEXT;
ALTER TABLE hr_messages ADD COLUMN lease_expires_at TEXT;
ALTER TABLE hr_messages ADD COLUMN attempt INTEGER NOT NULL DEFAULT 0;

SELECT * FROM hr_messages
WHERE state IN ('unread', 'decided')
  AND (lease_expires_at IS NULL OR lease_expires_at < :now)
ORDER BY priority DESC, created_at
LIMIT 1;
```

- 幂等键 = 主键或 `conversation_key:action`。
- 断点恢复 = 读状态，不读内存。
- 抢占 = 过期租约可覆盖；旧 `nonce` 一律拒绝。
- 批次游标存 `job_batches.cursor_json`（或等价字段），按 `dedupe_key` 定位，不存列表下标。

## 7 失败与重试

### 7.1 重试白名单

允许重试的场景：

| 场景 | 上限 | 依据 |
|---|---|---|
| `uiautomator dump` 返回 137 或空文件 | 1 次 | 旧实现 `adb.py:214-222` |
| 页面变化但未稳定 | 2 次，间隔 0.5 秒 | 动画 |
| 未读筛选面板未出现 | 1 次重按 | 日志：170 次应用中有 41 次重按 |
| 断连 | 只探测，不重放原命令 | `adb.py:100-103` |

不重试：方向不明、身份不唯一、菜单未出现、删除未核验、正文未落入。这些是 `unknown`，不是重试对象。

### 7.2 设备中断与重连

拔插不改变已经发生的事实，只改变证据还能不能拿到。规则：**能证明的才算，证明不了就是 `unknown`，绝不猜。**

#### 7.2.1 分阶段后果

| 阶段 | 拔掉时发生什么 | 正确结论 | 重插后 |
|---|---|---|---|
| 读屏 / 导航（未点击） | `adb` 报错，归类 `device_disconnected` | `failed`，可重来 | 重新选设备、重新读屏，从检查点继续 |
| 输入文本（未点发送） | 正文可能未写入 | `not_sent` | 核对输入框为空后再重来 |
| 点发送后、读到证据前 | 点击可能已生效，响应丢失 | **`unknown`** | 只能人工核对，禁止重发 |
| 确认框已打开、未点确认 | 弹框可能仍在 | `pending` | 重新读屏确认框状态 |
| 本地写库 | 事务未提交 | 回滚 | 无需恢复 |
| 心跳 / 持租约 | 进程可能已死 | 租约过期 | 过期抢占或人工 `recover` |

旧实现依据：`actions.py:843-845` 在 `tapped=True` 后任何异常都上抛，交由上层记 `unknown`，不降级为 `not_sent`；`scan.py` 的 `device_stop_result` 把断连收敛为可重派的暂停态。

#### 7.2.2 四条硬规则

1. **断连不等于失败，也不等于成功。** 区分 `device_disconnected`、`device_unauthorized`、`device_offline`（`adb.py:127-144`），分别决定重试、等授权或停止。
2. **不重放命令。** 远端非零退出或超时后只探测连接，绝不重发原命令（`adb.py:100-103`）。
3. **点击后断连即 `unknown`。** 写库、记原因码、生成核对卡；不自动重试，不换会话继续猜。
4. **重插不等于续跑。** 设备回来后先对账，再决定下一步。

#### 7.2.3 重连对账流程

```text
1. adb devices        → 状态必须为 device；offline / unauthorized 不算回来
2. 检查锁屏           → 未解锁则停，等解锁，不盲点
3. 恢复输入法         → 读当前 IME；若是 ADBKeyboard 且原值已知，切回
4. 读上一条动作状态    → pending / unknown 就停在核对，不继续
5. 重新读屏对账        → 页面、会话身份、未读是否变化
6. 才允许取下一条任务
```

输入法需要特别处理：旧实现 `actions.py:860` 在断连时跳过恢复（`if original_ime and not disconnected`），拔插可能把手机留在 ADBKeyboard 上。新设计应在切换前把原 IME 写入本地状态，使进程重启后仍能恢复。

#### 7.2.4 未读角标的预落库

打开未读会话会消耗角标。若在“打开之后、读完之前”断连，角标已消失、消息仍在，下一轮会误判为无未读。

因此必须在打开前持久化：会话身份、轮次、`opened` 标记、候选来源。重插后按身份定向重开（旧项目有 `--conversation` 路径），不得依赖角标。

#### 7.2.5 租约过期与抢占

- 租约必须有 `expires_at`，执行期间定期续租。
- 进程死亡后租约到期；只有确认原持有进程已停止才允许抢占（旧实现 `store.py:1068-1086` 校验 `--confirm-stopped`、PID、host、nonce）。
- 抢不到就停，不以“终端连不上”推断进程已退出。

#### 7.2.6 明确不做

- 不因拔插把动作标成 `sent` 或 `not_sent`。
- 重插后不自动重发上一条消息。
- 不把“设备回来了”当成“状态没变”：页面、未读、对方回复都可能已变化。
- 不把拔插当取消手段；取消应走租约释放或取消标记。

## 8 归档与删除

删除是唯一不可逆且无法语义纠错的动作，必须是规则触发：

1. 候选：`rejected` 且无 `keeps_contact`，或最后活动超过 N 天。
2. 保护项优先：未读、待发草稿、未核实动作任一命中则不删。
3. 身份核验：姓名 + 职位完全匹配；同名同职位不唯一则跳过。
4. 双阶段：先写台账（原因、时间、身份证据），再删除，删后核验目标消失且相邻锚点仍在。
5. 模型只能给出 `intent=rejected`，不能直接触发删除。

## 9 非目标

- 不做主 LLM 编排与逐条审核。
- 不做独立队列服务或后台常驻进程。
- 不做每消息一个子 LLM 或多个 agent 并行。
- 不把截图作为验收证据；截图只作为人工现场与读取兜底输入。
- 不让视觉模型产出点击或替代主路径读取。
- 不让模型决定归档、排序或预算。
- 不扩展真实自动发送授权；不可逆动作仍需当轮确认。
- 不做拔插后的自动续跑或自动重发；重连先对账。
- 不把职位批次当成不可分割任务；不在点击、输入、确认框期间抢占。

## 10 验收指标

| 指标 | 目标 | 口径 |
|---|---|---|
| 未读漏检率 | 0 | 四源交叉；任一为“有”即不得报无 |
| A 档自动回复率 | ≥ 90% | 按分档统计 |
| `unknown` 率 | < 5% | 每个 unknown 必须有核对卡 |
| 误发/重发 | 0 | 幂等键 + 不重试 |
| 单轮 ADB 调用 | 设上限（建议 ≤ 200） | 日志计数 |
| 单轮耗时 | 设上限（建议 ≤ 15 分钟） | 与预算一致 |
| 视觉兜底使用率 | 建议 < 5% | 超过说明第 1、2 级退化 |
| 视觉判读误判率 | 需人工抽检 | 以第 4 级人工结论为准 |
| 未读检查间隔与调度等待 | 正常流程每条职位检查；事务建议 ≤ 30 秒，另计检测与切页耗时 | 检查时间差 + `stage_preempted.waited_ms`；后者仅从首次观察起算；暂停单列 |
| 单轮抢占次数 | 建议 ≤ 5；再次触发则暂停本轮 | `stage_preempted` 计数 + `preemption_limit` 暂停原因，不允许绕过未读 |

## 11 权衡

| 取舍 | 代价 | 理由 |
|---|---|---|
| 固定优先级 | 预算不足时不灵活 | 排序是规则；灵活性收益低于不确定性成本 |
| 一次调用做意图 + 措辞 | 无法分别评测 | 减少转录损失；需要时再拆两次 |
| 复用业务表当队列 | 与表结构耦合 | 避免第二份事实源漂移 |
| 不逐条截图审核 | 缺少直观现场 | 证据以节点/状态为准；截图不可靠且涉及数据外发 |
| 视觉兜底只补位 | 成本高，可能外发截图 | 只在主路径 `undetermined` 时使用，且只输出字段 |
| 不重试判读失败 | 单轮产出可能偏低 | 重试会重复副作用或掩盖问题 |
