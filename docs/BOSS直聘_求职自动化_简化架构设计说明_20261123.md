# BOSS直聘求职自动化 简化架构设计说明

> 文件用途：把旧项目的失败证据、本次真机验证结论和“最简可行架构”合并成一份设计说明，供后续实现业务 CLI、运行时状态与设备执行器时对照。本文只描述结构与判据，不包含真实聊天内容、联系人、公司、薪资或联系方式，也不构成任何设备执行授权。

## 0 范围与依据

- 目标系统：单台 Android 手机、单条 ADB、串行执行；不做并行、不做无人值守的不可逆批量发送。
- 业务目标（使用者定义）：
  1. 浏览新职位，创造沟通机会。
  2. 读取并回复 HR 消息，判断意图。
  3. 归档已拒绝或过期的会话。
- 证据来源：
  - 旧项目代码静态阅读（`scripts/` 下 `core/`、`hr/`、`jobs/`、`heartbeat/`）。
  - 旧项目 `data/operations.log` 的事件名与原因码**计数**（仅聚合，未读取任何业务内容）。
  - 一次真机验证（BOSS 14.200、Android 15、1080×2400），记录见 [`BOSS直聘_实机验证偏差与修订建议_20261123.md`](BOSS直聘_实机验证偏差与修订建议_20261123.md)。
  - 旧项目操作手册：[`BOSS直聘_手机客户端原始操作_原子化分析.md`](BOSS直聘_手机客户端原始操作_原子化分析.md)。
- 本文是设计说明，不是实施计划；里程碑与排期另行编写。

## 1 背景：旧项目输在哪

### 1.1 失败分布

旧稿记录的历史聚合为：旧项目 apply 事务 352 次，LLM 判断错误（evidence_not_in_message + policy_violation）约 13 次，占 3.7%；其余主要归于页面、读屏与动作结果未知。旧稿“操作手册 §1.2”的引用有误，当前原子化分析该节是 UI 树解析，不含这些统计；本轮不读取历史日志，故保留数字作为未复核的历史背景，不用其证明故障比例或模型能力。

据此提出的设计假设是优先改善感知与程序状态；它不是对真实模型能力或失败因果的已验证结论。

### 1.2 三个根因

| 根因 | 代码证据 | 后果 |
|---|---|---|
| 循环变量住在 LLM 上下文（历史归因，待核实） | 旧稿误引“操作手册 §1.3”，当前该节实际是坐标、手势与按键，无此复盘证据 | 历史记录称单次 hr scan 输出 37 KB，本轮未复核；不据此断言所有失败成因 |
| 自动回复被策略层关死 | `policy.py:132-133` 禁止 `needs_human`/`uncertain` 发送；`status.py:12-13` 把约面试、薪资、背调、敏感信息都归入 `needs_human` | 大量真实 HR 场景只能出草稿，表现为“经常转人工” |
| 未读判定 fail-open | `message_list.py:264-269` 只认 `:id/badge_view`；`scan.py` 的 `_message_tab_badge` 读底部 tab 数字；`scan.py:1964-1979` 在角标读不到时按 0 处理并继续 | 读不到被当成“没有未读”，静默漏读 |

补充约束：

- `policy.py:14`、`apply.py:548`：首条回复必须含固定声明，否则 `policy_violation`。
- `policy.py:114-118`：决策 `evidence` 必须是原文子串。
- `policy.py:70-74`、`141-143`：规则引擎默认 `uncertain`，并可一票否决 LLM。
- `scan.py:1989-1990`：任一未核实动作会让整轮未读扫描停摆。

## 2 设计原则

1. **程序持有循环与状态**：队列、租约、重试预算、断点恢复都在 SQLite，不在模型上下文。
2. **模型只回答单条决策**：无状态、窄输入、受 schema 校验；不排序、不计数、不审核。
3. **照实分三态**：`ok / failed / undetermined` 必须分开，`undetermined` 不得当成“空”或“否”。
4. **只有不可逆动作需要原子化**：发文本、发简历、换微信、换电话、删会话；其余用少量设备原语组合。
5. **证据优先于文案**：系统行、槽位状态、节点增量是证据；弹框文案、Toast、截图不是。
6. **默认不重试**：只有可证明的瞬态错误才重试，其余停下并记原因码。

本文接口、状态与默认值均为待实现的开发契约。M0–M2 先按本文实现离线合成验证；生产策略与设备标定未确认时保持 `read_only`。不恢复旧业务 Skills：程序持有流程，提示词仅承担单次决策，操作手册指导人工使用；默认不创建三处 Skills 目录，与实施计划 §7 一致。

## 3 总体架构

```
┌──────────────────────────────────────────────┐
│ 传感器（程序）                                │
│  未读四源：行内数字 / 新招呼计数 / 底部角标 / 预览基线 │
│  职位候选、清理候选                            │
└───────────────┬──────────────────────────────┘
                │ 结构化候选（≤2 KB）
┌───────────────▼──────────────────────────────┐
│ 循环与队列（程序）                            │
│  任务级优先级：未读 > 新消息读取 > 职位 > 归档   │
│  安全点抢占 + 有界延迟 + 批次游标              │
│  租约、幂等键、重试预算、断点恢复              │
└───────────────┬──────────────────────────────┘
                │ DecisionEnvelope
┌───────────────▼──────────────────────────────┐
│ 单次决策（模型，无状态）                      │
│  意图 / 措辞 / 单条职位评估 / 异常裁决         │
└───────────────┬──────────────────────────────┘
                │ Decision（受校验）
┌───────────────▼──────────────────────────────┐
│ 执行与验收（程序）                            │
│  设备原语 + 5 个不可逆动作护栏 + 三态证据      │
└───────────────┬──────────────────────────────┘
                │ 仅 unknown
                ▼
         人工核对卡 / 下一轮
```

没有主 LLM，没有独立队列服务，没有逐条截图审核，没有多 agent 并行。

## 4 数据流与调度

### 4.1 一轮数据流

1. 传感器从业务表计算候选，合并多源未读证据；任一有效源为“有”即保守按有未读处理；只有满足 §5.3 的完整否定条件才报无，其余先定向核对、仍未知则暂停。读取按 §5.4 的四级阶梯逐级下降。
2. 循环按固定优先级取一条候选，写入租约（`lease_owner`、`lease_expires_at`）。
3. 程序拼装 `DecisionEnvelope`，调用一次模型；输出经 schema 与证据校验。
4. 程序按策略分档决定发送、草稿或转人工；不可逆动作走护栏。
5. 证据写回业务行，释放租约；`unknown` 标 `blocked` 并生成核对卡。动作未决或尚未到达安全点时整轮暂停；仅无设备副作用的语义待办可以只阻塞对应会话。

### 4.2 任务粒度与抢占

需求是“未读一直优先”。因此不能把职位批次当成一个不可分割的任务，否则批次运行期间到达的未读只能等待。

#### 4.2.1 任务粒度

| 对象 | 建模方式 |
|---|---|
| 一条未读会话发现 | 一个任务，打开前先保存发现，读全后绑定本次入站消息身份；不把角标计数拆成虚构消息 |
| 一条职位 | 一个任务（打开 → 采集 → 沟通 → 资源消息 → 回列表） |
| 一个职位批次 | 游标 + 预算，**不是任务**；可随时暂停与恢复 |
| 一条清理候选 | 一个任务 |

批次不再是调度单元。20 条职位是 20 个任务加一个游标。

#### 4.2.2 每次取任务重算优先级

```python
# 调度设计伪代码：状态未知先核对，每次只执行一个任务。
while budget_ok():
    refresh_candidates()  # 优先复用安全点取得的当前快照
    if unread_unknown() or unread_signal_without_target():
        verify_unread_once()
        if unread_unknown() or unread_signal_without_target():
            pause("unread_unverified")
            break
    if unread_pending():
        if switching_from_job() and preemption_limit_reached():
            pause("preemption_limit")
            break
        task = next_unread()
    elif new_messages_pending():
        task = next_new_message()
    elif jobs_pending():
        task = next_job()
    elif cleanup_allowed():
        task = next_cleanup()
    else:
        break
    run(task)  # 不可逆动作仍须满足本轮授权与护栏
    checkpoint()  # 只有 §4.2.3 的全部条件满足后才能再次取任务
```

优先级不是“整段顺序”，而是每个任务取用前重新判定。“新消息读取”指已有会话基线发生变化、但没有明确未读角标的候选，不是再次处理同一条未读消息；两类候选按会话身份与入站消息身份去重。伪代码只表达调度分支，不代表当前仓库已有这些函数。

`unread_pending()` 仅指可定位的 kind=unread 候选；`unread_signal_without_target()` 指行角标/新招呼/底部角标为正却没有可定位的未读目标，不把预览变化强行关联到全局计数。`unread_unknown()` 在无可定位未读目标且（unread_state=unknown 或上述三个源任一 unknown）时为真。只有 preview_delta 为正、身份明确且其它三源均已确认 absent/not_applicable 时才进入 kind=new_message 分支，虽然聚合 unread_state 保守为 present，仍不虚构未读角标；有可定位明确未读目标时可以先处理该目标。

持续存在可处理未读时，严格优先级仍可能让职位等待；本文不承诺职位无饥饿。达到轮次预算或抢占上限时保存游标并暂停，不通过降低未读优先级保证职位进度。

#### 4.2.3 只允许在安全点抢占

| 可抢占 | 不可抢占 |
|---|---|
| 一条职位处理完并已回到列表 | 点击发送/沟通的瞬间 |
| 输入框为空、无确认框 | 正在输入文本 |
| 无在途 ADB 命令 | 确认框已打开未确认 |
| 上一动作状态已写库 | 动作 `pending` 未收敛 |

左列条件必须同时满足，不是任选其一。`pending` 或 `unknown` 尚未核实时暂停并生成核对卡，不继续取任务。中途打断会留下“点了一半”的现场，正是 `unknown` 的主要来源之一。

“安全点”是上述条件全部成立且检查点事务已提交的时刻；“抢占点”是安全点上由职位切换至未读任务的调度机会，不是任意一条设备命令之间。其它任务结束时也须确认已返回对应列表；无后续任务时可以直接保存状态并结束轮次。

#### 4.2.4 抢占检查优先复用已有读取

职位任务结束回到列表时，优先复用该次读取中实际可见的消息角标；只有当前页面包含相应节点时，才能解析“新招呼”计数。快照缺少信号或已失效时走 §4.2.5，不能把信号缺席当成零，也不保证检查始终不增加设备调用。旧项目已有类似复用优化：提交 `8a25ac9 perf(hr): 复用发送后层级与返回列表快照减少重复读屏`。

#### 4.2.5 角标不可读时 fail-closed

1. 首次读不出：在安全点允许一次定向核对，切到消息页读取；有未读则留在消息页处理，确认无未读才返回职位列表。耗时纳入本轮预算，具体耗时待实测。
2. 仍读不出：暂停批次，记 `unread_unverified`，本轮不再执行不可逆职位动作。
3. 不做清理：清理依赖“无未读”前提，未读状态不明时一律不删。

#### 4.2.6 有界延迟

| 指标 | 目标 |
|---|---|
| 未读检查间隔 | 正常职位流程每完成 1 条就检查；事务建议 ≤ 30 秒 |
| 首次观察到未读 → 开始处理的调度等待 | 下一个安全点优先取未读；记录实测耗时 |
| 单条职位事务耗时上限 | 建议 ≤ 30 秒；超时停止发起后续动作，先核实在途结果并保存状态，再暂停，不强制中断 |
| 单轮抢占次数 | 建议 ≤ 5 次；再次需要抢占时保存游标并暂停本轮，不能继续职位或清理 |

“未读优先”的正常路径目标是**最多等待一条职位事务，再加检测与切页耗时**。轮询无法获知消息实际到达时刻，不能把首次观察时间当作到达时间；“到达后 ≤ 30 秒”目前不是可证明的硬保证。超时、状态未知或设备中断走暂停与核对，单独记录，不能算作按时开始处理。

#### 4.2.7 批次游标按身份恢复

列表会滚动、会插入新职位，下标不可靠。游标保存：

```json
{"batch_id": "...", "last_job_dedupe_key": "...",
 "visited_keys": ["..."], "remaining_budget": {"count": 12, "seconds": 420}}
```

恢复时按 `dedupe_key` 重新定位；找不到就跳过，不按“第 7 条”硬点。

#### 4.2.8 抢占记录

```json
{"event": "stage_preempted", "from": "job", "to": "unread",
 "job_key": "...", "trigger": "unread_count>0",
 "first_observed_at": "<timestamp>", "handling_started_at": "<timestamp>",
 "waited_ms": 12000}
```

`waited_ms` 是首次观察到未读至开始处理的耗时，运行内用单调时钟计算；时间字段用于本机审计。检测间隔另记连续检查的时间差。该事件在实际切换并开始处理时写入；超时、达到抢占上限或未能进入安全点则写暂停原因，不能伪造已开始处理的事件。没有这些记录，“优先”就无法被审计。

#### 4.2.9 不做

- 不在点击、输入、确认框期间抢占。
- 不杀进程来“抢占”。
- 不让模型决定抢占时机。
- 不让清理抢占任何阶段。
- 不把“整个未读阶段跑完”或旧快照中的“未读为空”作为启动职位批次的门槛；每条任务仍按当前候选优先级选择，未读状态未知先核对。

## 5 接口

以下均为新实现建议的 v1 契约；旧项目的同名字段仅作证据背景。`ReadResult` 是读取结果（§5.3），`Evidence` 是动作结果（§5.5），`DecisionEnvelope` 是给模型的一次请求（§5.1）；三者不共享状态枚举。

### 5.1 DecisionEnvelope（输入）

```json
{
  "schema_version": 1,
  "task_id": "<业务候选键>",
  "nonce": "<本次租约 UUID>",
  "input_hash": "<规范化请求的摘要>",
  "app": "boss",
  "kind": "hr_message | job_card | anomaly",
  "subject": {"conversation_key": "<hash>", "job_brief": "<一句话摘要>"},
  "inbound": "<本次要处理的原文>",
  "context": ["<可选的上一两条入站>"],
  "allowed_facts": [
    {"key": "work_location", "value": "<值>", "source": "user_confirmed", "expires_at": null}
  ],
  "policy_tier": "A | B | C",
  "constraints": {"max_chars": 300, "no_contact": true, "max_bytes": 2048}
}
```

约束：一次只含一个主体；所有事实带来源与有效期；不包含队列、日志、其他会话或截图。

示例中的 `a | b` 表示枚举，线上值必须只取其中一个。所有键必填、拒绝额外键：`schema_version` 为整数 1；`task_id/nonce/input_hash/app` 为非空字符串；`subject` 固定为 `conversation_key: string|null`、`job_brief: string|null`（HR 必须有会话键，职位必须有摘要）；`inbound` 为非空字符串，异常时为程序生成的原因摘要；`context` 为至多两条字符串；`allowed_facts` 每项固定 `key/value/source/expires_at`，`value` 为字符串，`source` 仅 `user_confirmed`，有效期为 UTC 时间字符串或 null；过期事实不入请求。`policy_tier` 由程序预先决定，缺少已确认策略时取 C。`constraints` 的三个字段分别为正整数、布尔、正整数，v1 固定 300/true/2048。

统一摘要函数 `H(value)`：先把 JSON 对象按键排序，以 UTF-8、`ensure_ascii=False`、分隔符 `(',', ':')` 序列化，再取 SHA-256 小写十六进制；不做隐式文本规范化。`input_hash` 为去掉自身字段后的整个请求摘要；最终完整请求按 UTF-8 不超过 2048 字节，超限记 `input_too_large` 并转待办，不截断 `inbound`。时间统一用 `YYYY-MM-DDTHH:mm:ss.sssZ`；UUID 使用带连字符的规范形式。键与摘要只在本机使用，不把摘要当作脱敏后的可公开业务数据。

### 5.2 Decision（输出）

```json
{
  "schema_version": 1,
  "task_id": "<原样回显>",
  "nonce": "<原样回显>",
  "input_hash": "<原样回显>",
  "intent": "rejected | declined | interested | needs_human | uncertain",
  "sub_intents": ["<受词表约束>"],
  "reply": "<text>",
  "evidence": "<必须是 inbound 的子串>",
  "escalate": null
}
```

所有键必填、拒绝额外键，前三个标识与输入逐字匹配；`intent` 取示例枚举之一；`sub_intents` 为去重字符串数组，v1 白名单为 `greeting / resume_request / job_question / interview / salary / jd_request / sensitive / non_text / ambiguous`（组合只用于说明意图，不扩大动作权限）；`reply` 为 0–300 个 Unicode 码点；`evidence` 为非空的 `inbound` 原样子串；`escalate` 为 null 或 `human_review`。`needs_human/uncertain` 必须 `escalate=human_review`，不得发送；无可引用原文则由程序直接建待办，不调用模型。

校验失败即丢弃该决策，不回写业务结论；本机审计记 `invalid_decision`，任务转 `blocked`。回显不匹配记 `stale_decision`；`evidence` 非子串记 `stale_evidence`。返回只接受一个 JSON 对象，禁止 Markdown 围栏。桥接超时 20 秒，仅可证明尚未提交请求的传输失败重试一次；提交后超时不重复调用，记 `decision_timeout`，无需推断模型是否处理。M4 只能使用显式配置且获准的模型桥，M0–M2 不调用模型。

### 5.3 ReadResult（三态）

```
ok           : 读到且结构完整（唯一列表、唯一输入框、身份一致）
failed       : 明确失败（页面不对、元素不存在、断连）
undetermined : 读到了，但无法判定（角标未知、方向不明、身份不唯一）
```

`undetermined` 不得参与“没有未读”“已经发送”“已经删除”的结论。

可实现的数据形状为 `ReadResult[T] = {status, value, reason_code, snapshot_id, observed_at, source, confidence}`。所有键必填、拒绝额外键；`status` 仅 `ok/failed/undetermined`，`ok` 时 `value:T` 且 `reason_code=null`，其它状态 `value=null` 且原因非空；`source` 仅 `hierarchy/pixel/vision/human/fixture`，`confidence` 仅 `low/medium/high`。`snapshot_id` 为规范 UUID；无法获取快照时为 null；`observed_at` 为毫秒 UTC 字符串。各字段分别读取，不要求列表页也有输入框；完整性由该接口所需字段决定。v1 `failed` 原因为 `device_disconnected/device_unauthorized/device_offline/wrong_page/invalid_xml/invalid_fixture`；`undetermined` 原因为 `unread_unverified/identity_ambiguous/incomplete_snapshot/stale_snapshot/uncalibrated_profile`，未知枚举拒绝。明确失败停止当前读取，不通过下一阶梯掩盖断连。

M2 的 `value` 为 `UnreadSnapshot`：`{app, profile_id, coverage, signals, rows, candidates, unread_state}`，所有键必填、拒绝额外键。`app` 固定 boss，`profile_id` 为非空字符串，`unread_state` 仅 `present/absent/unknown`；`coverage` 仅 `viewport/all`；四个 `signals` 固定键为 `row_badge/new_greeting/tab_badge/preview_delta`，每项为 `{state, count, reason_code}`，`state` 仅 `present/absent/unknown/not_applicable`，`count` 为非负整数或 null（bool 不算整数）。`present` 若有计数则须 >0，`absent` 的 count 固定 0，`unknown` 的 count 固定 null 且必须有原因码。`rows` 为数组，每项固定 `{conversation_key, identity_hash, preview_hash, time_hint, unread_count}`，前三项为非空字符串或 null，`time_hint` 为字符串或 null，计数为非负整数或 null；不足以唯一确定身份时会话键为 null，不能定位点击。`candidates` 为数组，每项固定 `{candidate_key, conversation_key, kind, source_names, fingerprint}`，键与指纹均为非空字符串，`kind` 仅 `unread/new_message`，`source_names` 为四源键的非空去重数组。指纹来自对应 row 的摘要、时间和计数；不能用来源总数生成行身份。

M2 区分结构失败与字段未知：XML 损坏为 failed/invalid_xml，唯一列表容器不存在为 failed/wrong_page，多个列表容器为 undetermined/incomplete_snapshot，profile 未标定为 undetermined/uncalibrated_profile，快照过期为 undetermined/stale_snapshot；这些状态 value=null，不保存部分候选。列表容器可解析但某行身份缺失、角标不可读或缺基线时，保留完整的 rows/signals 结构并返回 ok，未知字段用 null/unknown，不能因一行歧义丢掉其它行的明确正信号。ReadResult 的 confidence 在 ok 时为 high（只说明结构解析确定），未决/失败时 low；源内 unknown 仍由聚合门禁处理，high 不证明无未读。非法对象不得入库；合成输入校验失败统一 failed/invalid_fixture。

源内 `reason_code` 与 ReadResult 的原因词表分开：present/absent 为 null，unknown 取 `missing_signal/unverified_semantics/no_baseline/ambiguous_signal/uncalibrated_region/incomplete_coverage`，not_applicable 为 `profile_not_applicable` 且 count=null；不是新增 ReadResult.status。row_badge 在全覆盖各行均显式为零时才 absent，任一行为正则 present，其余 unknown；所有计数可读时 present.count 为合并后各行计数之和，否则为 null。preview_delta 对至少一行与已验证基线不同为 present（count 为已知变化行数，不声称总数），全覆盖且全部可比相同时为 absent，缺基线为 unknown；仅视口相同为 unknown/incomplete_coverage。比较规则固定为：双方 preview_hash 非空且不等即可证明变化；hash 相等时仅双方 time_hint 均非空才继续比较时间，时间不等为变化，相等为该行无变化；缺摘要/时间保留未知，不能用 null==null 证明无变化。同一源有多种未知时原因优先级为 ambiguous_signal、uncalibrated_region、unverified_semantics、missing_signal、no_baseline、incomplete_coverage；明确正信号优先于未知。解析器只给每源结论，领域聚合函数再合并；不能用未读条数相等来建立全局计数与行身份的映射。

每个身份唯一行仅在 unread_count>0 时产出 unread；否则仅在上述预览比较明确变化时产出 new_message。两者并存时合为 unread，source_names 保留 row_badge/preview_delta 中实际支持该行的来源。新招呼与底部角标是全局信号，M2 不将它们关联到任意行，也不把正计数拆成候选。合并后按 candidate_key 升序输出；rows 保持列表顺序。多个同身份且非分页重叠的行保留 identity_hash、置 conversation_key=null，不产生候选；分页合并后可以从唯一 identity_hash 重建会话键，再重算候选。全局信号未知但已有明确行角标候选可以处理，预览候选不能消解其它未读源的未知。

聚合规则按顺序执行，构成 M2 的独立判据：

1. 只合并同一 `app/profile_id/snapshot_id` 的信号；同一次列表遍历的滚动分页允许合并，其它导航、输入法/版式变化即失效，或距首屏采集超过 5 秒记 `stale_snapshot`（5 秒是离线开发基线，待真机标定）。now 早于 observed_at 也拒绝为 stale_snapshot，不能接受未来快照。
2. 任一有效信号 `present`，`unread_state=present`；即使另一源报 0 也不能报无。新招呼仅是保守的候选信号，不声称计数等于未读 HR 数。全局计数为正但无可定位行时，`candidates=[]`，必须定向核对，不从数字臆造会话。
3. 只有 `coverage=all`、至少一个适用源、所有适用源均 `absent`、无身份未知行且无未关闭发现时，才是 `unread_state=absent`。`not_applicable` 必须由已验证的版本 profile 显式声明，不能用于跳过缺失、未标定或语义待确认的源；全部不适用仍为未知。完整遍历首尾及每页可读性，或已标定可覆盖全列表的全局零信号，才可声明 `all`；仅一屏不能声明。全局零只能提供 coverage，不能把未观测的行角标或缺基线的 preview_delta 改成 absent。
4. 其余 `unread_state=unknown`；读取结构完整时仍可 `ReadResult.status=ok`，调度器检查 `unread_state`，一次定向核对后仍未知则整轮暂停。M2 不实现导航，把定向核对留给 M3；CLI 的 `stop_reason` 按实施计划 M2 的有序判据区分 `unread_unverified` 与 `needs_targeted_verification`，不能统一使用后者，本轮用合成快照验证这些出口。
5. 预览变化只产生 `new_message` 候选，不证明方向；无历史基线为 `unknown`，相同预览也不能单独证明没有新入站。明确未读与预览变化指向同一会话时合并为 `unread`，保留两种来源；消息读全后再按入站消息键去重。数字 TextView 必须位于已确认的行角标区域，不能把薪资、时间或正文数字算作未读；profile 未标定时返回未知。

全局汇总与可调度候选须分别检查：preview_delta=present 只能消解自身缺基线造成的未知，不能覆盖行角标、新招呼、底部角标中的未知；这些未知先走一次定向核对。某个明确未读正信号已有定位目标时可先处理该目标，不能因此宣告其它行无未读。M2 只报告此检查结果，实际切页仍在 M3。

该逻辑可在合成 profile 上完整实现；14.200 的“新招呼”语义和无 id 角标区域仍未验证充分，因此真实 profile 对这些字段保留 `unknown`，不阻碍离线 M2 开工，也不据此放行真实动作。

空列表只有 profile 明确验证了空态且 coverage=all 才能使行级源 absent；M2 最小 profile 不定义此空态，行角标与预览源先走 unknown/missing_signal，后续真实空态另行标定。层级/合成夹具确定解析字段使用 high，像素已标定字段使用 medium，失败/未决字段使用 low；confidence 不参与“多数投票”。M2 的应用、版本、snapshot_id 和时间均由采集上下文提供，不能由模型补写。

### 5.4 读取阶梯与视觉兜底

主路径永远是程序的结构化读取；视觉只在主路径判不出来时补位，且只输出字段、不产出操作。

#### 5.4.1 四级阶梯

| 级别 | 手段 | 触发 | 输出 | 可校验性 |
|---|---|---|---|---|
| 1 | 层级 XML（`uiautomator dump`） | 默认 | 页面、行、方向、身份、正文、按钮 | 高：节点与文本可复核 |
| 2 | 像素/几何（原始 `screencap`） | 层级不含该状态（如红点角标） | 有无未读、角标计数、控件是否禁用 | 中：依赖阈值与分辨率 |
| 3 | 视觉模型判读（截图） | 1、2 对该字段均为 `undetermined` | 页面类别、未读条数、控件状态 | 低：需交叉校验 |
| 4 | 人工核对 | 3 仍不确定，或涉及不可逆动作 | 结构化结论 + 现场截图 | 最高 |

每级结果都带 `source` 与 `confidence`。“低级别”在此指证据能力较弱的后续阶梯，不得覆盖前级已确认字段；跨级冲突记 `undetermined` 并转人工，不能凭高置信覆盖结构证据。视觉默认关闭；未启用则从第 2 级直达第 4 级。已启用视觉也须有独立的结构/像素证据交叉校验；无交叉证据时仍转人工，不因 `high` 单独放行。

#### 5.4.2 为什么第 2 级不是可选项

旧项目标定文档 `docs/未读状态图像识别标定记录_20261116.md` 记录：该设备/版本上 BOSS 没有把未读状态暴露给无障碍层级，唯一信号是头像右上角红点，只能像素采样；判据为 `badge_view` 区域强红像素 ≥ 100，核心色与容差需按机型重标定。

同一天的提交也说明单源不稳：

- `1f33da9` 未读识别改用 `badge_view` 红像素阈值判定
- `e6c28d1` 移除顶部分类计数兜底，未读只信像素判据
- `fe93ea3` 未读角标不可判定时用消息数字角标兜底，不静默当作无未读（提交说明记录了 2026-11-20 实测的 `no_more_unread` 假阳性与漏读）
- `a2a322d` 用视口像素覆盖 B 段与末页审计

2026-11-23 真机验证又出现第三种形态：未读是无 `resource-id` 的数字 TextView，并伴随“新招呼”的 `tv_count`。同一结论：信号形态随版本漂移，不能写死单源。

#### 5.4.3 视觉兜底的触发与输出

触发必须同时满足：

- 第 1、2 级对该字段均为 `undetermined`
- 该字段影响下一步决策（例如“有没有未读”“当前是不是聊天列表”）
- 不处于不可逆动作的发送后核验阶段

输入：一张当前屏幕截图 + 需要判定的字段清单。输出只允许结构化字段：

```json
{
  "page": "chat_list | chat_detail | job_detail | unknown",
  "unread_rows": 0,
  "badge_count": null,
  "confidence": "low | medium | high",
  "source": "vision",
  "notes": "<不超过 80 字，不得复述聊天正文>"
}
```

校验：字段必须在白名单内；`confidence=low` 或字段缺失时按 `undetermined` 处理；`notes` 不得包含原文片段。

#### 5.4.4 禁止用途

- 不作为“已发送/已删除”的证据：这类结论需要点击前后的时序对比，单张截图无法证明。
- 不直接产出点击坐标或操作指令。
- 不替代第 1 级的批量读取（成本高、不可复现）。
- 不在 `confidence=low` 时继续不可逆动作。

#### 5.4.5 隐私与授权

截图含真实聊天画面。默认走第 4 级本机人工核对；本机视觉模型也须显式启用。云端调用必须在核对实际待发送内容后取得本轮明确外发授权，并先脱敏姓名、公司与正文；脱敏或选择模型都不自动产生授权。

### 5.5 不可逆动作契约

| 动作 | 前置 | 幂等键 | 证据 |
|---|---|---|---|
| 发文本 | 正文回读一致、授权有效 | `app:message_key:reply` | 系统行/回显新增 |
| 发简历 | 确认框附件名匹配 | `conversation:resume` | “附件简历请求已发送”记 `request_sent`；“附件简历已发送”记 `sent` |
| 换微信 | 槽位可点击、未处理 | `conversation:wechat` | 槽位“请求中”/系统行 |
| 换电话 | 同上 | `conversation:phone` | 同上 |
| 删会话 | 身份唯一、保护项为空、已确认 | `conversation:delete` | 目标不再出现且锚点仍在 |

表中 `conversation` 指已含应用前缀的会话键，其余动作键为 `conversation:action`，拒绝重复请求；再次请求需人工核对后另立业务事件，不由过期租约解锁。统一流程：写 `pending` → 执行 → 判三态 → `unknown` 标 `blocked`，**绝不重试**。

M6 的职位沟通也使用同一 pending/授权/不重放协议，动作键为 `app:job_key:apply`，Evidence.effect=applied；并不是不受护栏限制的普通导航。

`Evidence = {action_key, outcome, effect, reason_code, before_snapshot_id, after_snapshot_id, observed_at}`：所有键必填、拒绝额外键；action_key 为非空字符串，快照 ID 为规范 UUID 或 null，时间为毫秒 UTC 字符串；`outcome` 仅 `performed/not_performed/unknown`，`effect` 仅 `sent/request_sent/deleted/applied/none`。只有本次前后变化足够证明且两个快照 ID 非空、不同时才 performed，effect 不得 none、reason_code=null；not_performed 必须 effect=none，reason_code 仅 `authorization_missing/precondition_failed/cancelled_before_action`；unknown 必须 effect=none，reason_code 仅 `device_disconnected/result_unverified/executor_interrupted`。非法组合视为 unknown/result_unverified，保留动作锁，不允许按未执行重试。ReadResult.undetermined 仅表示读不清：动作前使本次动作不执行；点击后使 Evidence 为 unknown，不能直接把读取 ok 当作 performed。

文本历史术语 `sent/not_sent/unknown` 分别映射至这三个 outcome，删除成功用 `performed+deleted`，不称 sent。`performed+request_sent` 只完成“发起请求”任务，不等于附件交付；后续交付单独核对。`unknown` 及崩溃残留的 `pending` 都保留动作键锁，生成人工卡 `{task_id, action_key, reason_code, snapshot_ids, allowed_resolutions}`：前两项为非空字符串，原因取 Evidence 的 unknown 词表，snapshot_ids 为去重 UUID 数组，allowed_resolutions 固定 `['confirm_performed','confirm_not_performed','abandon']`；放弃只关闭任务，不解除未决动作锁。M0–M2 不执行动作或生成此卡，M5 才实现锁与人工收敛，不提前创建动作模块。

### 5.6 策略分档

| 档 | 意图 | 处理 |
|---|---|---|
| A | 正向招呼、明确要简历、简单岗位问答 | 仅策略与本轮动作授权均有效且已开启 A 档时执行；否则草稿 |
| B | 约面试、谈薪资、要 JD、需要附件 | 生成草稿，人工一键 |
| C | 可疑、敏感信息、纯图片/语音、语义歧义 | 只登记待办 |

分档是配置，不是代码分支；模型无权改变档位。

档位只限制可执行范围，不替代授权。简历、联系方式、删除各需独立动作授权；仅批准文本回复不能批准附件或联系方式。M0–M2 固定只读，具体意图归属未确认时仅输出待办。

| 列 | 类型与约束 |
|---|---|
| `state` | `TEXT NOT NULL DEFAULT 'queued' CHECK IN ('queued','leased','running','done','not_sent','failed','blocked','cancelled')` |
| `priority` | `INTEGER NOT NULL DEFAULT 0`，仅同类型内降序；同分按 `created_at,key` 升序 |
| `created_at, updated_at` | `TEXT NOT NULL`，统一 UTC 格式见 §5.1 |
| `lease_owner, nonce, lease_expires_at, owner_host` | `TEXT NULL`，四者和 owner_pid 同时为空或同时非空；nonce 为每次获取新生成的 UUID |
| `owner_pid` | `INTEGER NULL`，持租约时为正整数，其余为空 |
| `attempt` | `INTEGER NOT NULL DEFAULT 0 CHECK(attempt>=0)`，仅成功 claim 时加一 |
| `reason_code` | `TEXT NULL`，`blocked/failed` 时非空 |

v1 使用 SQLite STRICT 表，INTEGER 拒绝 bool 参数，所有主键列显式 NOT NULL。状态与租约以 CHECK 联动：仅 leased/running 的五个租约字段全非空，其余状态全空；queued/leased/running/done 的 reason_code 必须 null，其余必须为非空原因码。baseline_preview_hash 与 verified_at 同空或同非空，baseline_time_hint 在未验证时为 null。所有摘要是 H 的完整输出；所有 app 固定 boss（未来应用经迁移扩展），键须匹配 app 前缀。UUID、时间格式、摘要及 JSON 字段由仓储入口严格校验，不靠 SQLite TEXT 类型推断；坏参数报 invalid_input 并整批回滚。source_names_json 是四源名的非空去重数组（按四源定义顺序保存）；opened 在 M1–M2 固定 0，不凭 start 虚构已打开会话。

必建索引为 `UNIQUE hr_conversations(app,identity_hash)`、`UNIQUE hr_discoveries(app,conversation_key) WHERE state IN ('queued','leased','running','blocked')`、`UNIQUE hr_discoveries(nonce) WHERE nonce IS NOT NULL`、领取索引 `hr_discoveries(app,kind,state,priority DESC,created_at,key)` 与审计索引 `events(app,subject_key,event_id)`。外键均 ON DELETE RESTRICT，不级联删除；M1–M2 不提供物理删除业务行的接口。nonce 同时关联任务与设备行，两个表的 owner/pid/host/nonce/截止时间必须一致；事务写入者维护此跨表不变量。隔离设备行是例外：任务已 blocked 且清空租约，设备行保留旧身份作隔离标记，禁止 claim。

events.event 在 M1–M2 仅取 `snapshot_upserted/candidate_superseded/candidate_deferred/task_claimed/task_started/lease_renewed/task_finished/lease_recovered`；payload_json 为固定对象 `{from_state,to_state,nonce,candidate_count}`，前两项为任务状态或 null、nonce 为 UUID 或 null、candidate_count 为非负整数或 null，禁止额外键和正文。事件 app/subject_key 对任务事件必填，其余可 null；原因仅使用本节任务/仓储原因词表。初始化不写事件；同指纹无变化重放不追加事件。后续动作/调度事件在相应里程碑扩展词表，不让实现者自选日志字段。

键规则统一使用 §5.1 的 H：会话键 `app:conv:H([联系人,公司,职位])`，仅对身份字段齐全且在当前列表唯一的行派生（合成姓名也按此规则）；缺字段或重复身份保留为未知行，不入可定位队列。指纹为 `H([preview_hash,time_hint,unread_count])`；发现键 `app:discovery:H([conversation_key,fingerprint])`，同一会话多来源只 upsert 一行且 `unread` 优先，不改变已有终态、不续租、不增加 attempt。M2 只保存摘要，合成 fixture 可以带正文供解析，但事件表不保存原文。相同指纹无法证明再次到达的新消息，不能自动生成第二个发送任务；该限制通过未知出口保留到 M3 的入站身份设计。

`identity_hash=H([联系人,公司,职位])`，`preview_hash=H(原样预览文本)`；不通过摘要恢复身份明文。会话表也校验 `(app,identity_hash)` 唯一。同一会话至多一个非终态发现；先查发现键是否已存在：终态键一律跳过，不能为它取消其它 queued 行；相同非终态键只合并来源，queued 可升级 kind 为 unread，其它状态不改 kind/指纹/快照/创建时间。只有新键确实不存在且旧发现仍 queued 时，才在同事务取消旧发现（reason_code=candidate_superseded）并插入新键。旧发现 leased/running/blocked 时保留原负载，只合并来源，记 candidate_deferred；下一安全轮次重采新快照，不能改写正在处理的输入。发现行初始 priority=0，时间来自本次 ReadResult.observed_at；重复行保持 created_at，只有内容实际改变才更新 updated_at。若新观察时间早于待改发现的 updated_at，整批报 invalid_input 并回滚，不能倒写时间。

任务状态集合为 `queued/leased/running/done/not_sent/failed/blocked/cancelled`。`queued → leased` 由 claim 原子提交；`leased → running` 在开始用例前提交；`running → done` 仅当只读处理完整或 Evidence 为 performed；明确无外部副作用但业务动作未执行为 `not_sent`，读取明确失败为 `failed`；不确定或待人工为 `blocked`。`done/not_sent/failed/cancelled` 为终态，不自动重入队；blocked 的人工出口是：凭证据收敛到 done/not_sent、放弃为 cancelled，或确认从未开始设备副作用后重新 queued。任何动作 pending/unknown 都不得直接 blocked→queued。每次变更须与事件在同一事务提交；终态及 blocked 清空任务租约，但未决动作锁保留（M5 引入动作表）。

最小 `StorePort` 调用时序与返回值：

1. `upsert_snapshot(result: ReadResult[UnreadSnapshot]) → list[str]`：只接受 status=ok、snapshot_id 非空的完整合成解析结果，一个事务保存所有可唯一定位的会话与发现；未知行不入库，但不妨碍其它正候选落库。重新计算键/指纹并验证来源及 app 一致性，失败 invalid_input。返回本次候选中写后仍 queued 的键（包括无变化重放），按 key 升序，不能把终态或被其它非终态挡住的键返回为可领取。不得用未验证预览覆盖 baseline_*；新会话基线全 null，M2 仅使用 manifest 的合成基线供比较，不把它冒充真实读全后基线写库。
2. `claim(app: str, kind: str, owner: {id: str, pid: int, host: str}, now: str) → Lease|null`：app 仅 boss、kind 仅 unread/new_message，owner.id 为本次进程启动 UUID，pid 为正整数，host 为本机 H(platform.node())（只存本机库，不输出）。BEGIN IMMEDIATE 内先查 primary 设备行，存在即 lease_busy（含过期或隔离行）；不存在再按 priority DESC,created_at,key 选 queued，无候选返回 null 且不写事件。条件更新到 leased、attempt+1、写相同 nonce 的设备行 reservation_state=held，与 task_claimed 事件一起提交。`Lease={app,key,owner,nonce,expires_at}`，键均非空、nonce 为新 UUID、expires_at=now+60 秒；后续 API 不信任调用方可变的截止时间，核对库中值。轮次优先级先由 §4.2 选 kind，SQL 不跨类型抢排。
3. `start(lease: Lease, now: str) → Lease` 仅 leased→running，不延长截止时间；`renew(lease: Lease, now: str) → Lease` 只对 leased/running 将任务和设备截止时间一起延至 max(原值,now+60 秒)，返回新截止时间，后续调用使用新 Lease。`finish(lease: Lease, now: str, state: str, reason_code: str|null, proof: ReadResult|Evidence) → 'updated'` 仅 running→done/not_sent/failed/blocked：done 要求 ReadResult.ok 或 Evidence.performed 且原因 null；not_sent 要求 Evidence.not_performed；failed 要求 ReadResult.failed；blocked 要求 ReadResult.undetermined 或 Evidence.unknown。后三态原因须与 proof.reason_code 相同；语义待办在 M4 增加独立入口，M1–M2 不以随意字符串伪造 proof。除非法 proof/参数报 invalid_input 外，三者均在一个事务内校验任务状态及任务/设备的 owner、pid、host、nonce、库中截止时间和 held 状态，且 now 小于两行截止时间；不符 stale_lease，任何一行更新未命中则回滚。重放 start/finish 或使用 renew 前的旧 Lease 也 stale_lease。finish 追加事件并清空任务租约；明确完成/失败可删除对应设备行，Evidence.unknown 则保留设备行并设 quarantined。M0–M2 的 proof 只使用合成对象，不触发动作。
4. `recover(lease: Lease, confirm_stopped: bool, now: str) → {status:'recovered',task_state:'queued'|'blocked'}`：事务内先核对当前任务仍 leased/running，任务/held 设备行与 Lease 的身份、nonce、截止时间匹配，再要求已过期、confirm_stopped=true，最后调用注入的本机停止检查器。leased 恢复 queued、清空任务租约、删除设备行；running 恢复 blocked/recovery_requires_reconciliation、清空任务租约，但设备行改为 quarantined 并保留旧身份，防止父进程死亡后遗留的设备子命令与新任务并行。所有变更及 lease_recovered 事件一起提交；隔离行不会被 TTL、再次 recover 或人工放弃自动删除，M0–M2 不提供解除隔离命令，M5 对账确认现场及在途命令均收敛后才扩展解除入口。旧 nonce 或重复恢复报 stale_lease；未过期报 lease_busy；未确认、非本机、停止未知/仍活动/权限不足报 owner_not_stopped，均不变更。

停止检查器是仓储内部依赖，调用方不能传 process_stopped=true。v1 只支持同机本地库，不支持共享目录或复制库后的跨机恢复；host 不匹配一律拒绝。Windows 用标准库 ctypes 调用 OpenProcess/WaitForSingleObject：已退出句柄或系统明确返回 PID 不存在才算 stopped，访问拒绝/其它错误算 unknown；非 Windows 用 os.kill(pid,0)，仅 ProcessLookupError 算 stopped。PID 被复用而当前存在时保守拒绝，不自动杀进程。leased 阶段禁止任何设备命令，必须先提交 start；running 即使父进程停止也不能证明子命令停止，故保持隔离。测试注入 stopped/alive/unknown 三值检查器，不读取真实 PID 或调用 ADB。

租约 TTL 60 秒、每 20 秒续租一次是开发基线；now 为规范 UTC 字符串，now>=库中截止时间即过期，失败 API 不改变行或 attempt。进程内用单调时钟安排续租，并比较墙钟与单调时钟的增量：相差超过 1 秒即 clock_changed、停止新动作；重启后不凭旧时间证明进程停止。数据库事务不得跨设备/模型调用，renew 可在下一命令前或有超时的子进程轮询中执行，无需新增后台消费者。

查询入口 `unresolved_conversations(app: str) → list[str]` 只接受 boss，只读返回 queued/leased/running/blocked 的去重会话键，按 key 升序；非法 app 报 invalid_input。sense 先解析并 upsert 提交，再立即查询未关闭发现，避免在采集前缓存空集合；M2 单消费者不在两步之间调度任务。调用无 IO 的 `aggregate_unread(snapshot: UnreadSnapshot, unresolved_keys: list[str]) → UnreadSnapshot` 执行 §5.3，只重算 unread_state，不改信号/候选。无效参数抛 ValueError，由 fixture 入口映射 invalid_fixture。解析器本身不查库，聚合结果才是 CLI 的最终 unread_state；安全点刷新时重新查询。

上述失败以 StoreError(reason_code) 抛出到 CLI 的安全错误出口（退出 2），不与成功字符串混用；仓储原因码固定为 `invalid_input/lease_busy/stale_lease/owner_not_stopped/clock_changed/store_busy/store_io_error/db_version_unsupported/migration_failed`。任务原因码仅为 ReadResult/Evidence 的非空原因，加 `candidate_superseded/recovery_requires_reconciliation`。参数类型、状态组合或跨 app 键不合法统一 invalid_input；磁盘/权限/非 SQLite 文件错误为 store_io_error，SQL/迁移失败不得伪造成功；全部校验在事务前或条件写入时完成，不输出 SQL 参数或原始异常文本。

M1 先建全局设备租约和 HR 业务行；离线测试用合成 owner/PID 与可注入时钟/进程存活判据，不接设备。SQLite 连接设置 foreign_keys=ON、busy_timeout=5000；写事务均 BEGIN IMMEDIATE，失败整体回滚；锁等待耗尽为 store_busy。user_version=0 且 sqlite_schema 无用户表/索引/视图/触发器才在同一事务内建五表、索引并设为 1，失败不得残留半套表。版本 1 打开时核对表、列、约束及索引与 v1 模板一致，缺失/篡改或未知版本、非空无版本库均报 db_version_unsupported；重复初始化不得改数据。M1 没有 1→2 升级，不预建迁移框架；回滚测试在空库建表中途注入故障，断言 user_version 仍 0 且无残留。未来升级先用 SQLite backup API 写不覆盖旧文件的本机备份，再在事务内迁移和改版本，失败保留原版本、报 migration_failed；不导入旧项目库。

运行数据统一存 `data/runtime/`（被忽略的本机产物），业务库为 `data/runtime/runtime.sqlite3`；不读取旧项目库或根 `config.json`。批次游标到 M6 存 `job_batches.cursor_json`，按 `dedupe_key` 定位，不存列表下标。

## 7 失败与重试

### 7.1 重试白名单

允许重试的场景：

| 场景 | 上限 | 依据 |
|---|---|---|
| `uiautomator dump` 返回 137 或空文件 | 1 次 | 旧实现 `adb.py:214-222` |
| 页面变化但未稳定 | 2 次，间隔 0.5 秒 | 动画 |
| 未读筛选面板未出现 | 1 次重按 | 日志：170 次应用中有 41 次重按 |
| 断连 | 只探测，不重放原命令 | `adb.py:100-103` |

不重试：方向不明、身份不唯一、菜单未出现、删除未核验、正文未落入。这些是 `unknown`，不是重试对象。

### 7.2 设备中断与重连

拔插不改变已经发生的事实，只改变证据还能不能拿到。规则：**能证明的才算，证明不了就是 `unknown`，绝不猜。**

#### 7.2.1 分阶段后果

| 阶段 | 拔掉时发生什么 | 正确结论 | 重插后 |
|---|---|---|---|
| 读屏 / 导航（未点击） | `adb` 报错，归类 `device_disconnected` | `failed`，可重来 | 重新选设备、重新读屏，从检查点继续 |
| 输入文本（已证明未点发送） | 正文可能未写入 | `not_sent`，设备现场未收敛则暂停 | 本轮确认后核对身份、输入框为空和 IME，再新建尝试 |
| 点发送后、读到证据前 | 点击可能已生效，响应丢失 | **`unknown`** | 只能人工核对，禁止重发 |
| 确认框已打开、未点确认 | 弹框可能仍在 | `pending` | 重新读屏确认框状态 |
| 本地写库 | 事务未提交 | 回滚 | 无需恢复 |
| 心跳 / 持租约 | 进程可能已死 | 租约过期，不代表可覆盖 | 按 §6 确认停止后 `recover`；running 转 blocked 并隔离设备 |

旧实现依据：`actions.py:843-845` 在 `tapped=True` 后任何异常都上抛，交由上层记 `unknown`，不降级为 `not_sent`；`scan.py` 的 `device_stop_result` 把断连收敛为可重派的暂停态。

#### 7.2.2 四条硬规则

1. **断连不等于失败，也不等于成功。** 区分 `device_disconnected`、`device_unauthorized`、`device_offline`（`adb.py:127-144`），分别决定重试、等授权或停止。
2. **不重放命令。** 远端非零退出或超时后只探测连接，绝不重发原命令（`adb.py:100-103`）。
3. **点击后断连即 `unknown`。** 写库、记原因码、生成核对卡；不自动重试，不换会话继续猜。
4. **重插不等于续跑。** 设备回来后先对账，再决定下一步。

#### 7.2.3 重连对账流程

```text
1. adb devices        → 状态必须为 device；offline / unauthorized 不算回来
2. 检查锁屏           → 未解锁则停，等解锁，不盲点
3. 恢复输入法         → 读当前 IME；若是 ADBKeyboard 且原值已知，切回
4. 读上一条动作状态    → pending / unknown 就停在核对，不继续
5. 重新读屏对账        → 页面、会话身份、未读是否变化
6. 才允许取下一条任务
```

输入法需要特别处理：旧实现 `actions.py:860` 在断连时跳过恢复（`if original_ime and not disconnected`），拔插可能把手机留在 ADBKeyboard 上。新设计应在切换前把原 IME 写入本地状态，使进程重启后仍能恢复。

#### 7.2.4 未读角标的预落库

打开未读会话会消耗角标。若在“打开之后、读完之前”断连，角标已消失、消息仍在，下一轮会误判为无未读。

因此必须在打开前持久化：会话身份、轮次、`opened` 标记、候选来源。重插后按身份定向重开（旧项目有 `--conversation` 路径），不得依赖角标。

#### 7.2.5 租约过期与抢占

- 租约必须有 `lease_expires_at`（接口返回 `expires_at`），执行期间定期续租，开发基线见 §6。
- 进程死亡后租约到期；只有确认原持有进程已停止才允许抢占（旧实现 `store.py:1068-1086` 校验 `--confirm-stopped`、PID、host、nonce）。
- 抢不到就停，不以“终端连不上”推断进程已退出。

#### 7.2.6 明确不做

- 不因拔插把动作标成 `sent` 或 `not_sent`。
- 重插后不自动重发上一条消息。
- 不把“设备回来了”当成“状态没变”：页面、未读、对方回复都可能已变化。
- 不把拔插当取消手段；取消应走租约释放或取消标记。

## 8 归档与删除

删除不能通过后续消息纠正，必须是规则触发且取得本轮删除授权：

1. 候选：`rejected` 且无 `keeps_contact`，或最后活动超过 N 天。
2. 保护项优先：未读、待发草稿、未核实动作任一命中则不删。
3. 身份核验：姓名 + 职位完全匹配；同名同职位不唯一则跳过。
4. 双阶段：先写台账（原因、时间、身份证据），再删除，删后核验目标消失且相邻锚点仍在。
5. 模型只能给出 `intent=rejected`，不能直接触发删除。

## 9 非目标

- 不做主 LLM 编排与逐条审核。
- 不做独立队列服务或后台常驻进程。
- 不做每消息一个子 LLM 或多个 agent 并行。
- 不把截图作为验收证据；截图只作为人工现场与读取兜底输入。
- 不让视觉模型产出点击或替代主路径读取。
- 不让模型决定归档、排序或预算。
- 不扩展真实自动发送授权；不可逆动作仍需当轮确认。
- 不做拔插后的自动续跑或自动重发；重连先对账。
- 不把职位批次当成不可分割任务；不在点击、输入、确认框期间抢占。

## 10 验收指标

本节是后续灰度目标，不能把建议数值当成已经确认的生产配置。M0–M2 离线验收采用实施计划 §4 的确定性命令和夹具判据；默认开发预算为每轮 900 秒、200 次设备调用、20 条候选、单条职位 30 秒、最多 5 次职位→未读抢占（第 6 次暂停），均在发起下一动作前检查，核实在途结果仍须完成并单列超支。离线测试用可注入时钟与计数器；这些默认值不授权设备或真实发送，生产启用前仍须确认 §12。

| 指标 | 目标 | 口径 |
|---|---|---|
| 未读漏检率 | 0 | 合成夹具独立标签中 present 被判 absent 的条数 / present 总数；unknown 单列，不当作检出；真实全量漏检率尚不可证明 |
| A 档自动回复率 | ≥ 90% | 授权和 A 档开关均有效的文本任务中 performed+sent / 合格任务总数；草稿不算发送 |
| `unknown` 率 | < 5% | Evidence.outcome=unknown / 已开始动作总数；每个 unknown 必须有核对卡 |
| 误发/重发 | 0 | 幂等键 + 不重试 |
| 单轮 ADB 调用 | 设上限（建议 ≤ 200） | 日志计数 |
| 单轮耗时 | 设上限（建议 ≤ 15 分钟） | 与预算一致 |
| 视觉兜底使用率 | 建议 < 5% | 超过说明第 1、2 级退化 |
| 视觉判读误判率 | 需人工抽检 | 以第 4 级人工结论为准 |
| 未读检查间隔与调度等待 | 正常流程每条职位检查；事务建议 ≤ 30 秒，另计检测与切页耗时 | 检查时间差 + `stage_preempted.waited_ms`；后者仅从首次观察起算；暂停单列 |
| 单轮抢占次数 | 建议 ≤ 5；再次触发则暂停本轮 | `stage_preempted` 计数 + `preemption_limit` 暂停原因，不允许绕过未读 |

所有比率分母为 0 时记 `not_measured`，不得记达标；报告区分 fixture/smoke/model/device 来源，现有参考回放不证明运行时指标。对真实性能目标的样本量与观察窗口仍须在 M8 灰度前确认，M0–M2 不以真实自动回复率为门槛。

## 11 权衡

| 取舍 | 代价 | 理由 |
|---|---|---|
| 固定优先级 | 预算不足时不灵活 | 排序是规则；灵活性收益低于不确定性成本 |
| 一次调用做意图 + 措辞 | 无法分别评测 | 减少转录损失；需要时再拆两次 |
| 复用业务表当队列 | 与表结构耦合 | 避免第二份事实源漂移 |
| 不逐条截图审核 | 缺少直观现场 | 证据以节点/状态为准；截图不可靠且涉及数据外发 |
| 视觉兜底只补位 | 成本高，可能外发截图 | 只在主路径 `undetermined` 时使用，且只输出字段 |
| 不重试判读失败 | 单轮产出可能偏低 | 重试会重复副作用或掩盖问题 |

## 12 待确认

1. 策略分档的具体意图归属（尤其“要 JD”“约面试”是否进 B 档）。
2. 归档的“过期”天数与最后活动口径。
3. 单轮时间预算、单轮未读条数上限。
4. 租约 TTL 与续租方式。
5. 首条回复的固定声明是否保留；若保留，如何避免它压垮自动回复率。
6. 是否需要保留截图作为人工现场（涉及真实聊天画面外发）。
7. 优先级的固定顺序是否直接写死，还是留一个配置项。
8. 是否引入视觉兜底；若引入，用本机模型还是云端，外发如何逐次授权。
9. 像素阈值与视觉判读字段的重标定周期，以及换机/换版本后的回归方式。
10. 重连后是否允许自动恢复只读任务；默认建议不恢复，先对账再继续。
11. 是否需要在每条职位结束检查之外增加更细安全点；确认单条职位事务的超时上限（建议 30 秒）、检测与切页耗时目标、单轮抢占上限（建议 5 次）。

以上均为生产启用前的待确认项，不得当成使用者既定偏好或授权。M0–M2 使用 §5–6 与 §10 的离线开发基线：固定未读 > 新消息读取 > 职位 > 归档、60/20 秒租约、只读、视觉关闭、禁止自动重连续跑；归档未设天数则禁用，不继承旧值。修改基线须同步实施计划与扩展说明；未确认项不阻塞合成夹具与租约实现。
