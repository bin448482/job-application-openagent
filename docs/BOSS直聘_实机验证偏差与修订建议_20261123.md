# BOSS直聘手机客户端 实机验证偏差与修订建议

> 文件用途：记录一次经使用者逐轮确认的实机验证，列出《BOSS直聘_手机客户端原始操作_原子化分析.md》与当前客户端不一致或被漏掉的 7 项，并给出修订位置、影响与验证状态。本文只描述 UI 结构、状态与判据，不复述聊天正文、联系人、公司、薪资或联系方式。

## 0 验证环境与边界

- 客户端：BOSS 直聘 `versionName=14.200`、`versionCode=1420010`（`targetSdk=33`）。
- 设备：Android 15，物理分辨率 1080×2400，单台设备（写作 `<serial>`），已解锁。
- 方法：`adb devices`、`dumpsys window`、`uiautomator dump` 读取本机 UI 层级，对照终稿的静态阅读结论；未运行旧项目代码，未读取旧项目 `config.json`、`data/`、数据库或日志。
- 操作均在当轮明确确认后进行；本文记录的是 UI 行为，**不构成任何执行授权**。
- 样本限制：单机型、单系统版本、单客户端版本、单个会话。结论不能外推到其他分辨率、ROM 或 BOSS 版本。

本文的验证状态指原验证轮次；R1 与本次 R2 仅复核文档，没有重连设备复现。§2–3 的“终稿第 N 行”保留为修订前坐标，后续以原子 ID 和章节为稳定定位；源码 `file:line` 不受本轮文档插入影响。M2 中 calibrated、semantics_verified、global_zero_verified 等 true 只用于独立合成夹具，不是本次设备验证的新增事实；真实 profile 仍按第 4 节五条待确认保留未知。

## 2 逐条说明

### V1 未读角标的节点形态与旧判定不匹配

**观察**：该行未读角标是一个 `android.widget.TextView`，`text="1"`，`resource-id` 为空，位置在会话行左端（头像区），不在右侧；列表顶部“新招呼”tab 上另有 `:id/tv_count` 的数字节点。

**对照旧实现**：`scripts/core/message_list.py:264-269` 只在行内查找 `resource-id` 以 `:id/badge_view` 结尾的节点；找不到时 `unread` 为 `unknown`。像素兜底同样要求 `badge is not None`（`:272-279`），因此无 `badge_view` 时两条路径都不会给出 `yes`。

**影响**：在未开启未读筛选、仅靠行内角标判断的路径上，本版本的未读行会被判为 `unknown`，可能被跳过或触发暂停；只有在 `unread_filter_verified=True` 时才会整行判 `yes`。

**建议修订**：`CORE-M01`（修订前终稿第 266-271 行）补充“行内已确认角标区域可存在无 id 的数字节点”，不能把任意数字节点（时间、正文、薪资）都当角标；区域未标定则未知。保留旧 `badge_view`/像素判据作为历史实现；新版本像素阈值须重新标定。`8.1-9`（修订前第 1860 行）记录头像区和无 id 的版本观察。

**状态**：已在本机 UI 层级复现；其他机型位置未验证。

### V2 “新招呼”入口未覆盖

**观察**：消息列表顶部筛选行为 `全部 / 新招呼 / 仅沟通 / 有交换`，其中“新招呼”带 `tv_count` 计数；本次未读会话正属于该分类。

**对照终稿**：全文 `新招呼`、`tv_count` 出现次数均为 0；`CORE-M08`（第 311-316 行）描述的是“筛选 → 未读 → 确定”的旧路径，`4.0`（第 849-866 行）也未把“首次招呼”列为独立候选来源。

**影响**：若“新招呼”与旧“未读筛选”不等价，则首次招呼可能既不在旧筛选结果里，也不被行级角标兜底覆盖，形成候选缺口。

**建议修订**：在第 4 节“范围、入口与前置状态”和 `CORE-M08` 补“新招呼”独立候选信号；**等价性验证前不得把它当作旧未读筛选**，不得设置 `unread_filter_verified=True`。计数为正保守触发核对，为零也不独立证明无未读；没有行身份时不虚构候选，完整规则见[设计说明](BOSS直聘_求职自动化_简化架构设计说明_20261123.md) §5.3。

**状态**：信号已观察；“是否等价于未读筛选”“旧 scan 是否已覆盖”均未验证，列入第 4 节待确认。

### V3 输入法切换后输入框坐标漂移

**观察**：切换默认输入法前，输入框 bounds 下边缘在屏幕底部附近；切换后键盘占位，输入框整体上移。首次按切换前坐标点击，读屏显示输入框 `focused=false`、文本仍为占位符；重新读取层级并按其当前中心点击后才获得焦点。

**对照旧实现**：`scripts/hr/actions.py:736-738` 在 `ime set` 之后立即用**切换前**层级里的 `inputs[0]` bounds 点击；真正稳妥的是 `:756-768` 的重试路径——重新读屏取新 `fields[0]` 的 bounds 再点。

**影响**：首点失败时正文不会落入输入框，若实现只做一次点击且不回读，会误判为 `needs_draft_clear`/`not_sent`，或在未校验正文的情况下继续。

**建议修订**：`CORE-I06`（第 360-365 行）补“切换输入法后输入框 bounds 可能变化，必须用切换后的层级重新取中心点”；`HRA-P05` 已有“回读正文一致”的判据，应保留为唯一放行条件。

**状态**：已复现。

### V4 发送控件只剩 ImageView 兜底

**观察**：输入框右侧有两个可点击节点，一个是无 id 的 `LinearLayout`，最右侧是 `ImageView`（无文本、无描述），本版本没有 `Button` 类，也没有“发送”文案。

**对照旧实现**：`scripts/hr/actions.py:417-459` 先筛“位于输入框右侧且纵向重叠”的可点击节点，再依次优先 `Button`、文本/描述含“发送”、最后 `ImageView`，取最深层唯一者。本版本前两级为空，实际只走 `ImageView`。

**影响**：判定依赖“发送控件是 ImageView”这一实现细节；若客户端改成无文本的普通 `View` 或增加同层可点击节点，会返回 `None` 并判 `not_sent`。

**建议修订**：`CORE-I08`（第 373-377 行）注明“14.200 下只有 `ImageView` 兜底可用，属单一实现依赖”；实现时应加一条“候选为 0 或 >1 时停止”的失败用例。

**状态**：兜底路径已在本机验证可用。

### V5 联系方式动作在当前版本走二次确认

**观察**：“换微信”“换电话”点击后均出现“确定与对方交换微信/电话吗？”确认框，框内显示脱敏号码，点“确认”后对应槽位变为“请求中”，聊天内出现“请求交换微信/电话已发送”系统行。

**对照终稿**：`HRA-A04`（第 1326-1332 行）把“确认框缺失时可能直接发送”作为可能分支，`HRA-A05`（第 1334-1340 行）只描述确认框路径。当前版本是确认框路径，但仍应保留“无确认框”分支，因为不同版本行为不同。

**影响**：若实现只按“点击即发”处理，会把确认框当成异常而停下；反之若假设一定有确认框，遇到直接发送的版本会漏掉二次确认的机会。

**建议修订**：`HRA-A04` 补“14.200 观察到二次确认框”的版本注记，并保留两分支；`HRA-P11`（第 1258-1261 行）的横向区间判据（电话 `0-270`、微信 `270-540`）保留为旧实现的静态证据。本轮观察只验证两个动作及确认框，不验证这两个旧坐标区间可复用于新执行器；真实写入 profile 必须另行标定。

**状态**：两个动作均已在本机验证。

### V6 弹框文案不能作为交付证据

**观察**：简历确认框写“附件简历将直接发送至Boss”，确认后聊天内系统行是“附件简历请求已发送”，槽位是“请求中”。

**对照终稿**：`HRA-P10`（第 1252-1256 行）已正确区分 `sent` 与 `request_sent`，并规定“确认框仍打开时框内文案一律不算交付”；但 `7.3`（第 1830 行）把简历动作描述为“交付附件简历”，偏重，容易被读成“点击即交付”。

**影响**：若实现把弹框文案或“点击成功”当作 `sent`，会错误关闭入站、错误防重，且无法发现对方尚未接受。

**建议修订**：`7.3` 改为“发起附件简历请求或交付；仅请求不等于交付，后续接受状态须另核对”。本次只验证了 request_sent，未验证对方接受后的完整路径；`HRA-P10` 的 sent 分支仍仅属代码静态证据。补充通用警告：“确认框/Toast 文案不作为交付证据，证据只取本次系统行、槽位变化与附件节点”。

**状态**：已在本机验证。

### V7 返回键可能被吞一次

**观察**：在聊天页发送 `KEYCODE_BACK` 后，`mCurrentFocus` 仍在 `ChatRoomActivity`；再次发送后才回到 `MainActivity`（消息列表）。

**对照终稿**：`0.2` 的“返回列表序列”（第 23 行）与 `CORE-A18`（第 224 行）要求返回后重新判定页面，但没有说明“一次返回可能无效”。

**影响**：若实现按一次返回就假定已回列表，后续定位会落在聊天页，表现为 `needs_list` 或 `conversation_not_found`。

**建议修订**：`0.2` 与 `CORE-A18` 补“返回可能被弹框或输入法层吞掉一次，必须以焦点/页面重判为成功条件，不能以按键次数为准”。

**状态**：已复现一次；不同弹框层级下的次数未验证。

## 4 待确认（不得当作事实）

1. “新招呼”tab 是否等价于旧“未读筛选”，以及首次招呼是否会进入旧 `scan` 候选。
2. 不同机型、分辨率、字体缩放下，行级角标是否仍在头像左侧、是否仍无 `resource-id`。
3. 发送控件在其他版本是否仍是无 id `ImageView`；是否存在同层第二个可点击节点。
4. 返回键被吞的次数是否与弹框、输入法、动画状态相关。
5. `tv_count` 的取值语义（是否等于未读会话数、是否包含非 HR 通知）。

以上 5 条已在 R1 关联到终稿现有第 8 节条目：第 1/2/5 项见 8.1-9，第 3 项见 8.2-7，第 4 项见 8.1-14；保留原 48 项编号，不以新观察关闭旧不确定项。它们不阻塞 M0–M2 合成夹具实现：未验证真实 profile 保持 unknown，不推断阈值或授权。

## 6 复现方式（只读）

命令中的 `<设备临时XML>` 为设备侧同一临时文件的路径占位符，复现前须由操作者替换；不在公开文档保留设备绝对路径。

以下仅为将来复现的命令示意，**只读探针也必须先说明动作、占用时长与是否独占并取得本轮确认**；未确认不运行 `adb devices`、不连接手机。本轮文档审核不执行此段。层级 dump 会在设备写临时文件并把可能含正文的数据拉到本机，“只读”仅指不发消息/不点击，不表示没有文件副作用。

```powershell
adb devices
adb shell dumpsys window | Select-String 'mCurrentFocus|isKeyguardShowing'
adb shell uiautomator dump <设备临时XML>
adb pull <设备临时XML> <本机临时目录>/ui.xml
```

只读步骤不需要点击；临时目录必须是本机被忽略的位置，层级不得提交或外发，复现结束按本机数据保留约定处理。涉及“打开会话/点击动作”的步骤会改变手机状态（消耗未读角标、向对方发出请求），须另行说明具体动作并逐轮确认，且不属于本文的复现范围。现有历史“已删除”记录只针对原验证轮次，不代替未来复现的数据处置。

## 7 脱敏说明

- 不包含聊天正文、联系人姓名、公司名称、薪资、联系方式、附件实名信息或截图。
- 观察用的 UI 层级文件属于含聊天正文的本机临时数据，验证结束后已删除，未进入仓库。
